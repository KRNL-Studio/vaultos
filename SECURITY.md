# Security policy and threat model

## Reporting

Please use [GitHub private vulnerability reporting](https://github.com/rohit3a/vaultos/security/advisories/new). Do not put live credentials, vault files, machine private keys, personal paths, or full audit logs in public issues. Send a minimal synthetic reproduction, affected version, expected behavior, and impact. There is no paid response SLA or bug bounty. Only the latest preview is maintained; fixes may require upgrading.

## Threat model

VaultOS keeps a developer's secrets on their own computer and lets their programs, agents and browser use them without handing out more than each needs. The parts that hold keys are one Rust owner process at a time (the desktop app, the background service, `vaultosd`, or the human `vaultos` CLI, which takes the owner lock and opens the vault itself when no owner is running) and the vault file. The window's pages call the desktop process through Tauri commands; everything else (`vaultos` while an owner runs, the MCP bridge, `vaultos-agent`, the browser extension's native host, `vaultos-ssh-sign`) asks the owner over a private socket. Who VaultOS defends against, and how far:

| Adversary | Can | VaultOS | Not covered |
| --- | --- | --- | --- |
| Someone with a copy of the vault file (a backup, a lost disk, the sync remote) | Read and change files at rest | Argon2id with a stored cost floor; with a Secret Key, the password alone is not enough; every box authenticated and bound to its place; a MAC over the file | A weak password without a Secret Key; replacing the whole file with an older copy |
| An agent with a token (MCP, `vaultos-agent`) | Ask the owner anything | Scopes, approved projects and folders, allowed commands, just-in-time grants, all checked in the owner; values never returned without `reveal`; run output masked | What an allowed program does with values it is given (see **Run scope**) |
| A program started with values | Read its environment | Clean environment, filtered `PATH`, process group killed, stopped on lock | Encoding values past the masker; a child that leaves the group |
| A web page or another extension | Script the page, frame it, message the extension | Fill only on the login's site by the browser-reported origin, trusted clicks in a closed shadow root, pairing confirmed by the human, agents refused | Once filled, the page has the value, as with any password manager |
| The sync remote or its host | Read, withhold, replay or change repository files | age encryption to pinned devices, signed manifests and heartbeats, rollback checks | Withholding pushes; which devices sync and when |
| Other users on the computer | Read shared folders, connect to sockets | 0700/0600 permissions, socket peer uid check, session token | Root |
| A hostile import, env or template file | Feed parsers odd bytes | Size limits and fuzzed parsers; an import is parsed into a preview without touching the vault | |
| Software running as you, root, or a debugger | Read memory, files, tokens, the Keychain | Locked and zeroed key memory, hardening against core dumps and debuggers where the OS allows | This is the trusted local account boundary below |

Access changes (agent grants and revocations, approvals, browser pairing, sync trust), imports, exports and every use of a value by an agent, a program, the browser or an SSH client are recorded in the signed `audit-v4.log`. Creating, editing and deleting items and projects are not audit entries; item versions are kept in the encrypted history. The sections below give the details; [docs/audit](docs/audit/README.md) maps each boundary to the code that enforces it.

## What VaultOS protects

VaultOS 0.3 is written in Rust: the desktop app (a Tauri shell around the same pages), the agent API, the CLIs, the MCP bridge and sync all use `crates/vaultos-core` and vault format v4. See [the architecture notes](docs/ARCHITECTURE.md) for the key hierarchy.

- **Unlocking.** Argon2id (256 MiB, 3 passes, 4 lanes; about 0.9 s on an Apple M2) derives a key from the master password, and HKDF-SHA256 turns it into the Account Unlock Key. The parameters are read before anything is authenticated, so a file asking for less than 19 MiB and 2 passes, or for more than 1 GiB, 16 passes, 16 lanes or four times the default's memory × passes (a few seconds), is refused before Argon2id runs. The Account Unlock Key unwraps a random Vault Key, so changing the password re-wraps one key and re-encrypts nothing else. A strong unique passphrase remains essential against offline guessing.
- **Secret Key.** Optional, chosen per vault: 128 random bits shown as `VK1-` and 30 Crockford base32 characters with a 20-bit checksum. With one, the Account Unlock Key needs both the password and the Secret Key, so a stolen vault file cannot be guessed at from the password alone. The file stores only a 32-bit fingerprint, to say which key is missing. The desktop keeps the Secret Key in the Keychain or Secret Service on devices where you entered it. Settings → Secret Key adds, replaces or removes it and saves the Emergency Kit, a one-page PDF with the key; each needs the master password, checked in the app's Rust handler, and adding or replacing a key writes its kit to a new 0600 file before the vault changes. The kit is as sensitive as the key. Losing both the Secret Key and every unlocked device loses the vault; there is no recovery service.
- **Encryption.** The Vault Key wraps one key per project. Item metadata and item secrets are sealed separately with XChaCha20-Poly1305 and a random 192-bit nonce; the associated data names the purpose and the vault, project and item ids, so a box copied to another place in the file does not open. Listing and searching decrypt only metadata.
- **Items.** Concealed and one-time code custom fields are sealed with the item's secret, not its metadata, so listing, searching and Watchtower's age and expiry checks never open them. The Rust process computes one-time codes; Quick Access asks it to copy one and never receives the code. Agents never receive custom secret fields, even with `reveal`, and archived or trashed items are absent for them: listing, search, injection, reveal, project counts, pending approvals and `compare` leave them out or report them as not found, and an agent cannot overwrite, import over, delete or bring one back. `compare` hashes leave secret custom fields out, so they cannot be tested against guesses.
- **Attachments.** Each file is sealed with its project's key in its own XChaCha20-Poly1305 box under `attachments/` (mode 0600), with associated data naming the attachment, vault, project and item, and its SHA-256 is kept in the sealed metadata and checked on every open. Attachments are not synced, backed up by `vaultos backup` or exported. Removing one deletes its file, which is not secure erasure.
- **Integrity.** The whole file carries an HMAC-SHA256 under a key derived from the Vault Key, computed over the parsed file written again in a fixed canonical form ([docs/audit/CRYPTO.md](docs/audit/CRYPTO.md#file-mac)), so whitespace and field order are not authenticated but every value is. Removing, reordering or rolling back any part, or adding unknown fields anywhere (sealed boxes included), fails the unlock. This does not detect replacement of the whole file with an older complete copy (for example, a restored backup).
- **Audit chain.** `audit-v4.log` lines are Ed25519-signed and each names the hash of the line before it. The signing seed is sealed under the Vault Key and its public key is in the file, and every save records the newest entry in the vault, so editing, reordering or cutting the log short is detected. Entries written after the last save can be lost unnoticed. Anyone who can unlock the vault can sign new entries; the chain shows tampering by someone without the password, not by its owner. Appends, resets and set-asides take one lock (`.audit-v4.log.flock`) and appends follow the last entry on disk, so two processes writing to one vault keep a single chain. A log that fails verification at unlock is checked again, under that lock, before the next save or audit entry. If it is sound by then it simply continues; if another process reset it after this one unlocked, that new chain is followed; otherwise it is moved aside (`audit-v4.set-aside-*.log`) and a new chain starts with a signed `audit_log_reset` entry naming the problem, which that save anchors. A save never records "no head" over a damaged log. Entries hold names, actions and actors, never values. An entry is written before the change it records is saved, so a failed save can leave an entry for a change that did not happen, never a change without one. A new agent or approver token is written to its file only after the vault saves it.
- **Memory.** The Vault Key and keys derived from it are held in locked memory where the OS allows (`mlock`), are zeroed when dropped and are never printed by `Debug`. The sync identity (age key and signing seed) is zeroed when dropped and never printed, but is held in ordinary memory for as long as the vault is unlocked, so the OS can swap it to disk. Passwords, Secret Keys, sealed-secret plaintext, revealed values and decrypted records are zeroed when dropped; delegating, adopting and approving change metadata without opening the secret. A value being edited, restored by Undo or carried through an upgrade also passes through JSON values (history payloads) that are not zeroed. The owner zeroes each reply's JSON after sending it, and the clients zero the raw replies they read; values a client parses out of a reply live in ordinary strings until it exits. Every program that holds values or tokens (the app, `vaultosd`, `vaultos`, `vaultos-agent` and `vaultos-mcp`) calls `hardening::harden_process`: it turns off core dumps, makes the process undumpable on Linux (no same-user `ptrace` or `/proc/<pid>/mem`) and, in release builds on macOS, refuses debugger attachment. `vaultos-ssh-sign` does not: it holds no key, only passes data to sign and the signature over the SSH agent socket, and stays readable so the app can name it when asking to sign. Values given to a command run with secrets are in that command's environment, which it does not harden. Software running as your account, root or a compromised OS still reads an unlocked vault.
- **Desktop pages.** The window and Quick Access are the system webview (WKWebView on macOS, WebKitGTK on Linux) showing only the app's own pages, with a restrictive CSP (`default-src 'self'`, no fonts, objects or framing), a frozen JavaScript prototype, and no Node.js or other runtime in the page. Links and redirects never navigate a window, and new windows are refused. The pages reach the Rust process through two commands; each call is accepted only from its own window at its own page and, unless it is public, only after a human unlock. Quick Access has its own `quick:` calls: it can unlock, search metadata and ask the Rust process to copy, open a website or show an item. It never receives a secret value, and neither window can call the other's channels. Web developer tools exist only in debug builds.
- **Agent API.** The process that owns the vault (the desktop, the background service, or `vaultosd`) serves HTTP/1.1 on a Unix socket, `vaultosd.sock` in the private data directory, or, when that path is too long, in `$XDG_RUNTIME_DIR/vaultos` or `vaultos-UID` under the temporary folder, which must be a real directory owned by you with no group or other access. It refuses connecting processes of another user (checked with the peer's credentials) and requests with browser headers. Every route except `/status` needs the random session token in `daemon.json` (mode 0600); agent routes also need an enrolled agent token. Clients accept only a `daemon.json` that names this data directory's socket or its private fallback. Project, folder, scope, and record ownership checks apply in the owner; the MCP bridge and `vaultos-agent` hold no vault state. Request sizes and timeouts are bounded.
- New agents have only `read` and `inject` scopes, no approved projects, and no approved folders until the human chooses them. Empty scopes mean no permissions. Raw reveal is separate. Agent-created records await human approval before injection.
- All-access grants (`allProjects`, `anyRoot`) are explicit, default-off agent fields set only in the desktop or the password-authorized `vaultos` CLI; no agent request can set them. `allProjects` includes projects created later. `anyRoot` lets the agent read env files from and write exports to any path the account can write except the vault data directory (compared after resolving symlinks), which can overwrite unrelated files. Treat it as close to full account trust within the agent's scopes.
- The optional approval relay (`POST /pending/decide`) is off until a human stores the SHA-256 of a random relay secret with `vaultos approver set`. It requires the session token plus that secret (compared in constant time), never accepts agent tokens, and can only approve or remove records awaiting approval. Anyone holding the relay secret and able to reach the socket can approve agent-created keys, so keep its token file private to the relay.
- `vaultos` admin commands require the master password and claim exclusive ownership of the vault; they never print agent or relay tokens and write them only to mode-0600 files.
- File exports use private permissions, bounded serialization and atomic replacement. Agent paths must stay within approved canonical folders and cannot traverse observed symlinks. Shell export quotes values as data; dotenv output must be parsed as dotenv, not sourced as shell.
- Passwords are not put in command-line arguments. Optional remembering uses the macOS Keychain through the Security framework, or libsecret's `secret-tool` over stdin on Linux, and never falls back to a plaintext password file. Both use the preview's separate service namespace. Without a usable Secret Service, Linux background access is unavailable.

## Boundaries and limitations

**Trusted local account.** Malware, root, a compromised OS, debuggers, or other software running as your account can read memory, files, clipboard contents, session/agent tokens, and potentially Keychain items. That includes another agent's token file, such as a per-agent default under `<data directory>/agents/`; an agent with filesystem access can therefore act as any agent whose token it can read. VaultOS does not isolate a coding agent from your operating system. An agent with filesystem access can read injected credentials. An approved folder is an application permission, not a kernel sandbox.

**Unlocked state.** Decrypted metadata stays in the owning process while unlocked; secrets stay sealed until revealed. A value you reveal or edit also reaches the window's page, where JavaScript strings are not zeroed. Lock revokes the API and clears the window, but OS swap and crash capture are outside this guarantee. A copied value is cleared from the clipboard after 30 seconds or at Lock, if it is still there, but clipboard managers may keep copies. On macOS copies are marked with the `org.nspasteboard.ConcealedType` and `TransientType` conventions, which well-behaved clipboard managers skip, and restricted to this Mac so they do not reach Universal Clipboard; they are cleared only if the pasteboard has not changed since. On Linux the copy is plain text and is cleared only if it is still the same text. Clearing is best effort: neither platform offers an atomic compare-and-clear, so a copy made in the instant between the check and the clear can be cleared, and on Linux a later copy of identical text is cleared too. Manually exported files remain after lock.

**Remembering.** Background access is off by default. Turning it on lets the background service decrypt without a human typing a password. Manual Lock, and screen lock, sleep and idle under the default hard lock policy, write a persistent block (`locked` in the data directory) and remove the remembered item; a subsequent human unlock allows it again. Closing the window locks it without removing the remembered item. Disk/Keychain failures can prevent persistence; if both the block and the removal fail, the app says so in a notification. A Lock withholds the reply to a window call or agent request still running, and a copy that finishes after it copies nothing. Application termination cannot revoke copies of secrets already obtained.

**Service mode.** `VaultOS --service` (optional, installed only by running `scripts/install-service-macos.sh` or `scripts/install-linux.sh --enable-service`) keeps the vault served whenever no desktop window owns it. It decrypts only with the remembered password (and the Secret Key the device keeps), so it does nothing unless background access is on; it stops when that setting is off or the remembered password no longer opens the vault, and waits while a manual lock's block is present. Once it owns the vault it checks the block again, uses a kept Secret Key only if it is the one the vault's header names, and after decrypting checks the vault's own encrypted setting, so a password left in the keychain after background access was turned off is removed rather than used. It never holds the owner lock while waiting, stands back when a window asks for the vault, and takes it again after the window closes. While it runs, the vault is decrypted in a long-lived process that does not observe screen lock, sleep or idle time, and enrolled agents keep their grants. Its log contains operational messages, not values.

**Soft lock.** `lockPolicy` is `hard` by default: screen lock, sleep and 15 idle minutes stop the API, block background unlock and remove the remembered password. Choosing `soft` in Settings makes those three triggers lock only the window; the vault stays decrypted and the API keeps serving enrolled agents while the computer is locked, asleep or idle. Anyone or anything that can act as your account in that time can use existing agent tokens. The **Lock** button remains a full lock in both policies. The policy is enforced in the Rust process. On macOS, sleep and the session moving to another user lock the vault as soon as the system announces them; the 2-second watch also catches a screen lock and a gap in its own clock after sleep. On Linux screen lock is read from logind's `LockedHint`, which most screen lockers set.

**Touch ID.** Off by default, macOS only, and offered only when the system reports that Touch ID can prompt. Three settings: *unlock* opens the window with Touch ID by opening a copy of the master password sealed to a Secure Enclave key, then running the normal unlock checks. The key is a P-256 key made in the Secure Enclave, usable only after a Touch ID match with the fingerprints enrolled when it was made (`biometryCurrentSet`) and only while the Mac is unlocked, on this Mac only; the password is sealed to it with ECIES (AES-GCM). `touch-id-unlock.json` in the data directory holds the enclave's wrapped form of the key, which no other Mac and no software can use without the enclave and a match, and the sealed password. It is written after each password unlock (and password change) while the setting is on, removed when it is turned off, and removed when it no longer opens the vault, for example after fingerprints change; the next password unlock writes it again. Touch ID unlock does not need background access and reads nothing from the Keychain except the Secret Key the device keeps; *auto-prompt* asks when the window opens (never right after Lock); *human actions* requires a Touch ID success, a typed master password or an unlock within the last 30 seconds before revealing, copying or exporting values, approving keys for `.env`, adopting or delegating keys, enrolling, re-issuing or revoking agents, changing agent scopes or project/folder access (including all-projects and any-folder), trusting a sync peer, changing the master password, and saving settings that weaken protection (background access, soft lock, autosync, an export password, turning Touch ID confirmations off or Touch ID unlock on). The Rust process enforces this; when Touch ID is unavailable or cancelled it refuses with `NEED_PASSWORD` and accepts the master password, verified in memory with backoff, instead. Locking resets the 30-second window. Manual Lock and hard automatic locks remove the remembered password and write the `locked` block, so the next unlock needs the typed password; only closing the window or a soft lock leaves Touch ID unlock available. A plaintext `touch-id` file in the data directory records only that Touch ID unlock is on, so the lock screen can offer it; the encrypted setting is checked again after decryption. On Linux, or a Mac that cannot show Touch ID, the controls are hidden and the human-actions setting, if on, falls back to the master password. Touch ID guards the desktop window only. It does not protect a password remembered for background access from software running as your account, does not apply to the API, CLI or MCP bridge, and does not stop anyone or anything that can act as your account from using existing agent tokens while the vault is unlocked.

**Menu bar and Quick Access.** With the menu bar item on (the macOS default), closing the window locks the vault: the API stops, decrypted state is cleared and the owner lock is released, so the background service or the admin CLI can take over. The process then stays in the menu bar with nothing decrypted until a human unlocks from the window or Quick Access, which is the same human unlock with the same checks. The Quick Access shortcut is a system-wide hotkey; it shows the panel and grants nothing by itself. The menu bar and notifications show counts and status, never key names or values. `desktop-prefs.json` in the data directory is plaintext (mode 0600) and holds only the menu bar, shortcut, open-at-login and notification choices; software running as your account can change it. Open at login is off by default; turning it on writes a per-user LaunchAgent (`org.vaultos.preview.desktop`) or an XDG autostart entry that starts the app locked in the menu bar and does not enable background access.

**Owner controls.** The session token authorizes `/unlock`, `/lock`, `/shutdown` and `POST /sync`. Requests carrying an agent token are refused on these routes, so an agent cannot sync, lock or stop the owner through its own grants; `/sync` cannot accept conflicts and returns no values. The session token is readable by software running as your account, so these are local-account controls, not agent permissions. `/status` without the session token reports only whether the owner runs, is locked, its version and format, and public sync health (`enabled`, `state`, `halted`, `lastSyncAt`, `peerStalled`).

**Linux.** Linux builds have less runtime coverage than macOS. An unlocked login keyring hands the remembered password to any process in your session that asks the Secret Service for it. The optional systemd user unit keeps the vault served after the desktop closes, with the same remembered-password limits.

**Metadata.** Names, usernames, emails, URLs, notes, expiry dates, and project counts are visible through metadata scopes and may enter agent conversations. Do not place credentials in metadata. The audit log contains names, actions, actors, and times, not secret values. Encrypted history retains previous values. Deletion is not secure erasure of backups/history.

**Availability and durability.** Remote failures, local disk loss, interrupted writes and concurrent edits may prevent progress. Atomic writes and stale-writer checks reduce accidental overwrites but do not replace tested backups. Password rotation across multiple backup files is not transactional; verify its per-file results and retain both passwords until complete. No recovery service exists. A pull that changes the vault first copies `vault.enc` to `backups/`; the newest 20 of those copies, and any from the last 30 days, are kept and older ones are deleted, so keep your own backups for anything older.

**History.** To support Revert, the encrypted vault's history keeps each change's old and new values, including secret values. It is capped at 2,000 entries or 1 MB, whichever is reached first, by dropping the oldest. A copy of the vault or a backup includes that history.

**Trash.** Deleting moves an item to the Trash with its values and history intact, and the Trash syncs as an edit. Deleting it for good (confirmed by the human), emptying the Trash, or 30 days in it (checked at each human unlock in the app, `vaultos` or `vaultosd`) removes the item and every history entry about it, including those from before it moved, writes a tombstone and records a `purge_secret` audit entry. A device that pulls the tombstone removes its own history of the item too, unless the item lives on in another project (a move). Older vault copies and backups still contain it. Listing the Trash and an item's versions are the human's only.

**Breach check.** Off until the human chooses **Check now** in Watchtower, each time. The Rust process then sends, over HTTPS with `curl` (ignoring curl's configuration files and reading at most 1 MB of reply), the first five hexadecimal characters of each password's SHA-1 to `api.pwnedpasswords.com/range/` and compares the padded reply locally. Have I Been Pwned learns those prefixes and the requesting address, not the passwords.

**Imports.** 1Password, Bitwarden and CSV exports are read and parsed in the Rust process, at most 64 MB, with bounded ZIP and CSV parsing; nothing in them runs. The export file itself is plaintext and stays where it was: delete it once the import is done.

**References and `vaultos run`.** With no owner running, `vaultos read`, `render` and `run` open the vault themselves with the master password. While the app owns the vault they ask it through `POST /human/values`, which refuses agent tokens and, because the session token is readable by your account, needs on every request either the master password (and Secret Key) or a Touch ID confirmation naming the requesting program's full path and process id. Nothing is cached between requests. The service mode and `vaultosd` have no Touch ID and always need the password. `render` writes a new 0600 file atomically and refuses the data directory. `run` puts values in the command's environment, where the command and its children can read, log or send them. Output masking replaces each value of 4 characters or more, including one split across reads, but not encoded, transformed or partial copies; `--no-masking` turns it off.

**Run scope.** Off for every agent until the human grants `run` and lists the commands it may run. A command must begin, word for word, with an allowed entry and runs in an approved folder. The owner (the app, service mode or `vaultosd`) checks the request, reads the values and starts the command itself through `POST /run`; the agent, `vaultos-agent` and the MCP bridge get back only the exit code and up to 64 KB of each output stream, masked, never the values. The command gets a clean environment: the owner's `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `TZ` and locale variables, the values, and a `PATH` made from the caller's that leaves out missing, relative, temporary and world-writable folders and anything inside the working folder, the agent's folders or the vault's data, where an agent could put a program named like an allowed one. A bare program name is found in that `PATH` by the owner, and the audit entry names the program it found; an allowed entry that starts with an absolute path pins the program. Values under four characters cannot be masked reliably, so the command does not get them; the reply lists them in `tooShortToMask`. It runs in its own process group with no stdin. At most four commands run at once, and each is stopped (SIGTERM, then SIGKILL) at its timeout (at most ten minutes), when the owner stops or drops the request, or when the vault locks; a run during which the vault locked, even if it was unlocked again, is answered 423 with its output withheld. When the program exits, anything it left running in its group is killed; a child that starts its own session (`setsid`) escapes the group and is not, though its output is no longer read. Stopping the owner waits up to ten seconds for running commands to end before it locks the vault and releases it. The allowed program does receive the values, and its arguments, the folder's files and the caller's `PATH` can make it print, write or send them in a form masking misses: allowing `sh -c` or an interpreter is close to allowing `reveal`, and so is a command the folder's files define (`npm test` runs the folder's scripts). Treat each entry as trust in that program with any arguments in those folders. Each run is audited with the entry and the folder.

**Leak index.** `leak-index.json` (0600) holds a random key and, for each value, password and concealed field of 8 to 4096 characters (and each long line of a multi-line value), a 16-byte HMAC-SHA256 under that key with the ids of the item it came from; no values or names. Anyone holding the file can test guesses offline, so keep it as private as the data directory. It covers archived and trashed items and changes only when the human rebuilds it. A scan finds values written whole as one word (split on spaces, quotes and brackets, and after the first `=` or `:`); encoded, split or partial values are missed. Naming the items behind findings needs the vault. The desktop's folder scan uses an index kept in memory.

**SSH agent.** Off by default. Turned on in Settings, the app listens on `ssh-agent.sock` (0600) in the data directory, or in the private socket folder when that path is too long, and accepts only your user. It lists public keys only while unlocked and never adds, removes or exports a key; only unencrypted Ed25519 keys in SSH key items are served. Each signature needs Touch ID, or the app's Allow dialog where Touch ID is unavailable, naming the key, what is signed (a Git commit or tag, a login as a user, other SSHSIG data) and the program's full path. An approval covers that program (by executable path) and key for 10 minutes or until the vault locks, so anything that runs the same program in that time can sign with that key without asking. `vaultos-ssh-sign` hashes the message itself and asks the agent to sign it; every other mode, and keys VaultOS does not hold, go to `ssh-keygen`. Each signature is audited (`ssh-sign`).

**Just-in-time access.** An agent can ask for scopes on one project for 1 to 60 minutes. The human confirms with Touch ID or the app's dialog, which names the agent, the scopes, the project, the minutes, the requesting program and the agent's own stated reason. On Linux, VaultOS's own programs (`vaultos-mcp`, `vaultos-agent`, `vaultos`) are undumpable, so the app cannot read their path and shows only "a program" and its process id. The grant applies to that project only, never lets the agent create projects, lives only in the owner's memory, and ends when it expires, when the vault locks, when the owner stops, or with End temporary access. Grants are audited (`access-grant`). One confirmation shows at a time, and an agent the human declined must wait a minute before asking again. The background service and `vaultosd` cannot confirm and refuse requests.

**Browser extension.** Chromium browsers only (Chrome, Chromium, Brave, Edge, Arc, Helium, Vivaldi). Nothing happens until you load the extension, register its helper (`vaultos browser install`, or Set up browsers in Settings → Browsers) and pair the browser. The helper's manifest lets only the VaultOS extension's ID start `vaultos-browser`, which relays the extension's messages to the owner with the session token and the extension's origin as Chromium reports it. Pairing shows a code in the extension; the human confirms with Touch ID or the app's dialog, which shows the same code and the requesting program, and after a declined pairing new ones are refused for a minute. The pairing key is kept in the extension's own IndexedDB, which pages and content scripts cannot open, and as a hash in the encrypted vault; every request must carry it from the origin it was paired from, and agent tokens are refused on these routes. The owner offers a login only on its own site: the page's registrable domain under the Public Suffix List (so `alice.github.io` is not `bob.github.io`), and the saved port when the login's address names one, over HTTPS; or the exact host and port for `localhost` and IP addresses, where http is accepted only for `localhost`, `*.localhost` and `127.0.0.1`. Within a site every subdomain is offered the site's logins (a login for `admin.example.com` is offered on `shop.example.com`), so each login in the menu shows the host it was saved for, and logins saved for the page's own host come first; a site whose subdomains belong to different people, and which is not in the Public Suffix List, should keep its logins apart by port or not use the extension. It offers login items only, never archived or trashed ones, and lists names and usernames without values. The page address it checks is the sending frame's, as the browser reports it, never one the page's script supplies. Filling sends the username, password and current one-time code to the extension, which types them into the page; from then on the page and its scripts have them, as with any password manager, so a compromised page on the login's own site can take them. The extension's controls are in a closed shadow root, and act only on a real click on a control the browser has reported visible, uncovered and unaltered (Intersection Observer v2) for at least 0.4 seconds, so a page cannot press them, hide them under its own content or swap one in under the pointer; a page can still imitate them, or draw its own button that looks like VaultOS's. The toolbar popup is the browser's own window, which no page can cover. The extension fills only a form with one password field, never a field for a new password or one that is hidden or off the page. After a person submits a form with a password (not a page's script), the extension keeps that username and password in the browser's session storage (memory only, which content scripts cannot read) for two minutes, then deletes them, and at once when the tab closes. The next page offers them only when it shows no sign-in form (a form shown again usually means the password was refused): **Update** when the site has one login with that username, or the one just filled, naming it and its project; **Save** for a new login in the Logins project; nothing when several logins could be meant. Nothing is saved until you choose. Pairings, fills and saves are audited (`browser-pair`, `browser-fill`, `browser-save`); unpair in Settings → Browsers. Software running as your account can register its own native messaging host or use the session token directly, as with agents. The extension is loaded unpacked, and its ID comes from the public key in its manifest, which anyone can copy: another unpacked extension with that key gets the same ID, so the helper and the owner cannot tell it from VaultOS's. Load only the folder inside VaultOS, and approve a pairing only right after you chose **Pair with VaultOS** in that extension; a store-signed extension would close this, and needs a Chrome Web Store listing. Safari and passkeys are not supported.

## Upgrading from format v3

Nothing upgrades automatically. The upgrade runs only when the owner asks (**Upgrade this vault**, or `vaultos upgrade`): it copies `vault.enc` to `backups/vault-v3-<time>-<hash>.enc` and flushes it to disk, writes the new chain's first audit entry, decodes the new file again with the password and compares it with the original (history must match exactly, less only the oldest entries the 1 MB cap would drop), and replaces the vault last, only if it did not change meanwhile. An error therefore leaves the v3 vault in place, except one saying the change was saved but not confirmed on disk: then v4 is in place (the same holds for every save, which keeps its new state and any new password or Secret Key in that case). `audit.log` is left as it is, with the v3 backup. The backup is readable by VaultOS 0.2 with the earlier password. Reading format v3 (AES-256-GCM under scrypt) exists only for this upgrade.

## Sync format 2

- **Keys.** Each device's age X25519 identity and Ed25519 signing seed are sealed inside the encrypted vault (`sync_keys`), with the trust pins. Stealing the data directory and the sync repository without the password (and Secret Key, if set) does not decrypt synced records. Password rotation re-wraps the vault key but does not change these keys or protect old Git history.
- **Repository contents.** Records and tombstones are age files encrypted to every recipient in `recipients.txt`, under names that are the SHA-256 of their record ids. Every recipient must be a device this one trusts, or encryption is refused. Manifests are Ed25519-signed lists of ciphertext digests with a counter per device. Each file entry names the push (device and counter) that wrote that ciphertext, and each manifest records the newest push of every other device it had accepted. They carry no plaintext hash or content fingerprint, so the repository does not enable guessing low-entropy values. They still expose record counts, device labels and ids, timing and ciphertext sizes. Signatures are domain-separated from each other and from the audit chain.
- **Verification.** A pull or push refuses unsigned or modified ciphertext, unknown files in sync's folders, untrusted or changed device keys, a manifest whose counter went backwards, and a committed `.gitignore`, `.gitattributes` or `.gitmodules` anywhere in the checkout. A file is accepted only if a manifest signs it and no manifest that had seen the push which wrote it lists it differently or not at all, so an older ciphertext put back from history is refused even when a stale manifest still signs it. A manifest that names a push newer than that device's manifest in the checkout, or a device whose manifest is missing, is refused as a rollback. A push refuses to commit when Git would store other bytes than sync wrote (a filter or line-ending rule in `.git/info/attributes`, say), and refuses to push over a rebase that brought in a Git control file. A missing file is refused while any manifest still lists it as current, even if a tombstone of the same name exists. Sync signs, reads, commits and deletes only files under the names it writes; a file that only the local checkout has, such as Finder's `.DS_Store`, was made by your account and is left alone.
- **Rollback limits.** The local index (`sync-index.json`) is keyed and authenticated with keys derived from this device's signing key: it holds no plain record hashes, and a modified one stops sync. It also remembers the newest manifest seen from each device. Without it, a device can be shown a complete, consistent older state of the repository that no other manifest contradicts; the manifests' seen counters catch a rollback only when another device had already seen the newer push. `vaultos backup` copies the index with the vault, so a restored device keeps that memory. This is not a transparency log.
- **Merging.** A deletion yields only to a later edit (the record's `updatedAt`), on either device, not to a later push of the same record, so a device that missed the deletion and re-encrypts the record cannot bring it back, and an edit made after the deletion is kept everywhere. Concurrent edits need explicit acceptance before merging.
- **Trust.** First contact needs out-of-band comparison of identity fingerprints. Every trusted device is a full participant with all synced records, not a per-project collaborator. There is no revocation yet: removing a device or rotating keys means a new sync repository and new enrolments. Use a private repository.
- **Autosync.** Off by default and enabled only by the human (Settings, or `vaultos sync auto on`). It retries only network failures, a busy vault and, up to three times, a failed commit; anything else halts it with an audit entry (`sync_halted`) until a human acts. It never accepts conflicts. A pull that changes the vault first backs up `vault.enc` and applies all changes in one save. Git's error text is logged and audited with any user name, password or query string in a remote URL masked. Stopping the owner waits for a round in progress (each Git command has its own time limit) before it locks the vault and releases it.

## Assurance

This is a preview, unsigned and unnotarized unless its release notes say otherwise, and not an independently audited password manager. Automated tests cover encryption failures, stale writes and reloads, ownership/scopes, socket authentication, owner-only requests, service hand-over and manual-lock blocking, unsafe export paths and shell values, sync tampering/replay/conflicts, autosync halting, and the desktop flow (setup, reveal, lock, unlock races, Quick Access isolation, close-to-menu-bar and lock on sleep). Fuzz targets for the parsers of untrusted input and for masking run briefly on every pull request and for ten minutes each nightly, and known-answer vectors pin the format's key derivations, file MAC key and box encryption (not its canonical form or the audit and sync signatures). Tests, fuzzing and dependency advisories cannot establish that all vulnerabilities are absent. See release notes for exact validation and outstanding platform coverage. For a reviewer, [docs/audit](docs/audit/README.md) collects the cryptographic specification, test vectors and trust boundaries with the code that enforces each.

The desktop follows the [Tauri security guidance](https://v2.tauri.app/security/). Contributions that weaken these boundaries require explicit design discussion and regression coverage.
