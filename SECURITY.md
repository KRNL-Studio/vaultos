# Security policy and threat model

## Reporting

Please use [GitHub private vulnerability reporting](https://github.com/rohit3a/vaultos/security/advisories/new). Do not put live credentials, vault files, machine private keys, personal paths, or full audit logs in public issues. Send a minimal synthetic reproduction, affected version, expected behavior, and impact. There is no paid response SLA or bug bounty. Only the latest preview is maintained; fixes may require upgrading.

## What VaultOS protects

- A copied, locked `vault.enc` requires its passphrase to decrypt. Writes use authenticated AES-256-GCM with a fresh 12-byte nonce; the envelope includes a 16-byte authentication tag. The 16-byte salt is random when a password is set or changed. While unlocked, a process keeps the derived key for the vault's current salt and reuses both for its writes, so a save does not repeat the scrypt derivation. Lock zeroes that key buffer; changing the password picks a new salt.
- Envelope v2 derives a 256-bit key with scrypt (`N=131072`, `r=8`, `p=1`, maximum memory 256 MiB). Older envelope v1 can be read with its original `N=32768`; a new write uses v2. Vault schema v3 rejects unsupported newer readers/writers. A strong unique passphrase remains essential against offline guessing.
- The Electron renderer has a sandbox, context isolation, no Node integration, a restrictive CSP, denied navigation/popups/permissions, and an IPC sender-and-unlock check. The Quick Access panel is a second sandboxed window with its own preload and `quick:` channels, accepted only from that window's main frame at its own page; it can unlock, search metadata, and ask the main process to copy, open a website or show an item. It never receives a secret value, and the main window cannot call its channels (or it the main window's). Packaged fuses disable RunAsNode, Node options and inspection arguments, and require the embedded application archive.
- The local HTTP service binds only to `127.0.0.1`. Private routes require a random session token and an enrolled agent token; browser-origin requests and unexpected Host headers are rejected. Project, folder, scope, and record ownership checks apply at the service boundary. Request sizes and timeouts are bounded.
- New agents have only `read` and `inject` scopes, no approved projects, and no approved folders until the human chooses them. Empty scopes mean no permissions. Raw reveal is separate. Agent-created records await human approval before injection.
- All-access grants (`allProjects`, `anyRoot`) are explicit, default-off agent fields set only in the desktop or the password-authorized admin CLI; no agent request can set them. `allProjects` includes projects created later. `anyRoot` lets the agent read env files from and write exports to any path the account can write except the vault data directory (compared after resolving symlinks), which can overwrite unrelated files. Treat it as close to full account trust within the agent's scopes.
- The optional approval relay (`POST /pending/decide`) is off until a human stores the SHA-256 of a random relay secret with the admin CLI. It requires the session bearer token plus that secret (compared in constant time), never accepts agent tokens, and can only approve or remove records awaiting approval. Anyone holding the relay secret and able to reach the local API can approve agent-created keys, so keep its token file private to the relay.
- Admin CLI commands require the master password and claim exclusive ownership of the vault; they never print agent or relay tokens and write them only to mode-0600 files.
- File exports use private permissions, bounded serialization and atomic replacement. Agent paths must stay within approved canonical folders and cannot traverse observed symlinks. Shell export quotes values as data; dotenv output must be parsed as dotenv, not sourced as shell.
- Passwords are not put in command-line arguments. Optional remembering calls a native Keychain helper on macOS, or libsecret's `secret-tool` on Linux, over stdin and never falls back to a plaintext password file. Both use the preview's separate service namespace. Without a usable Secret Service, Linux background access is unavailable.
- Sync uses age and Ed25519 signatures, locally pinned public keys, approved recipients, ciphertext digests, and remembered manifest counters. Tampering, unknown peers, missing signed content, and observed replay cause refusal. Sync signs, reads, commits and deletes only files under the names it writes. Any other file in `records/`, `tombstones/` or `manifests/` that arrives in a commit is refused as unsigned (one in `machines/` or `peers/` is never read, and the next push removes it from the repository); one that only the local checkout has, such as Finder's `.DS_Store`, was made by your account and is left alone wherever it is. A `.gitignore`, `.gitattributes` or `.gitmodules` in the checkout stops a push instead, since it changes what Git commits. Existing content conflicts require explicit acceptance before merging.

## Boundaries and limitations

**Trusted local account.** Malware, root, a compromised OS, debuggers, or other software running as your account can read memory, files, clipboard contents, session/agent tokens, and potentially Keychain items. That includes another agent's token file, such as a per-agent default under `<data directory>/agents/`; an agent with filesystem access can therefore act as any agent whose token it can read. VaultOS does not isolate a coding agent from your operating system. An agent with filesystem access can read injected credentials. An approved folder is an application permission, not a kernel sandbox.

**Unlocked state.** Plaintext exists in the main process and, on human reveal/edit, the renderer. Lock revokes APIs and clears references and UI state, but JavaScript garbage collection does not guarantee memory zeroization; OS swap and crash capture are outside this guarantee. A copied value is cleared from the clipboard after 30 seconds or at Lock, if it is still there, but clipboard managers may keep copies. On macOS a native helper marks copies with the `org.nspasteboard.ConcealedType` and `TransientType` conventions, which well-behaved clipboard managers skip, and restricts them to this Mac so they do not reach Universal Clipboard; it clears only if the pasteboard has not changed since. Without the helper (Linux, or a missing helper) the copy is plain text and is cleared only if it is still the same text. Clearing is best effort: neither platform offers an atomic compare-and-clear, so a copy made in the instant between the check and the clear can be cleared, and on the plain-text path a later copy of identical text is cleared too. While unlocked, the owning process also keeps the plaintext of sync records it has decrypted, so an unchanged record is not decrypted again on every pull; it is tied to the in-memory vault and dropped with it on lock or reload. Manually exported files remain after lock.

**Remembering.** Background access is off by default. Turning it on lets a backend decrypt without a human typing a password. Manual lock writes a persistent block and attempts to remove the remembered item; a subsequent human unlock allows it again. An unlock reads the remembered item and rewrites it only when it is missing or holds a different password. Disk/Keychain failures can prevent persistence. The separate headless backend does not monitor screen-lock events; screen/sleep locking applies while the desktop is running. Application termination cannot revoke copies of secrets already obtained.

**Service mode.** `backend.cjs --service` (optional, installed only by running `scripts/install-service-macos.sh`) keeps a backend available whenever no desktop window owns the vault. It decrypts only through remembered Keychain access, so it does nothing unless background access is on; it exits when that setting is off and waits while a manual lock's block is present. It never holds the owner lock while waiting, hands the vault to the desktop when a window unlocks, and reclaims it after the window closes. While it runs, the vault is decrypted in a long-lived process that does not observe screen lock, sleep or idle time, and enrolled agents keep their grants. It reloads `vault.enc` if another process replaces it (under the write lock, and only when it holds no unsaved changes), so it never writes over a newer file. Its stderr log contains operational messages, not values.

**Soft lock.** `lockPolicy` is `hard` by default: screen lock, sleep and 15 idle minutes stop the API, block background unlock and remove the remembered password. Choosing `soft` in Settings makes those three triggers lock only the window; the vault stays decrypted and the API keeps serving enrolled agents while the Mac is locked, asleep or idle. Anyone or anything that can act as your account in that time can use existing agent tokens. The **Lock** button remains a full lock in both policies. Closing the window releases ownership without removing the remembered password in both policies, as before. The policy is enforced in the main process.

**Touch ID.** Off by default, macOS only, and offered only when Electron reports that Touch ID can prompt and background access (the remembered password) is on. Three settings: *unlock* opens the window with Touch ID by reading the remembered password from the Keychain and running the normal unlock checks; *auto-prompt* asks when the window opens (never right after Lock); *human actions* requires a Touch ID success, a typed master password or an unlock within the last 30 seconds before revealing, copying or exporting values, approving keys for `.env`, adopting or delegating keys, enrolling, re-issuing or revoking agents, changing agent scopes or project/folder access (including all-projects and any-folder), trusting a sync peer, rotating the master password, and saving settings that weaken protection (background access, soft lock, autosync, an export password, turning Touch ID confirmations off or Touch ID unlock on). The main process enforces this; when Touch ID is unavailable or cancelled it refuses with `NEED_PASSWORD` and accepts the master password, verified in memory with backoff, instead. Locking resets the 30-second window. Manual Lock and hard automatic locks remove the remembered password, so the next unlock needs the typed password; only closing the window or a soft lock leaves Touch ID unlock available. A plaintext `touch-id` file in the data directory records only that Touch ID unlock is on, so the lock screen can offer it; the encrypted setting is checked again after decryption. On Linux, or a Mac that cannot show Touch ID, the controls are hidden and the human-actions setting, if on, falls back to the master password. Touch ID guards the desktop window only. It does not protect the remembered password from software running as your account, does not apply to the API, CLI or MCP bridge, and does not stop anyone or anything that can act as your account from using existing agent tokens while the vault is unlocked.

**Menu bar and Quick Access.** With the menu bar item on (the macOS default), closing the window locks the vault exactly as before: the API stops, decrypted state is cleared and the owner lock is released, so a service backend or admin CLI can take over. The process then stays in the menu bar with nothing decrypted until a human unlocks from the window or Quick Access, which is the same human unlock with the same checks. The Quick Access shortcut is a system-wide hotkey; it shows the panel and grants nothing by itself. The menu bar and notifications show counts and status, never key names or values. `desktop-prefs.json` in the data directory is plaintext (mode 0600) and holds only the menu bar, shortcut, open-at-login and notification choices; software running as your account can change it. Open at login is off by default; turning it on writes a per-user LaunchAgent (`org.vaultos.preview.desktop`) or an XDG autostart entry that starts the app locked in the menu bar and does not enable background access.

**Owner controls.** The per-run session token in the private `session.json` authorizes `/shutdown` and `POST /sync`. Both refuse browser origins; `/sync` also refuses any request carrying an agent token, is not exposed as an MCP tool, cannot accept conflicts and returns no values. The session token is readable by software running as your account, so these are local-account controls, not agent permissions.

**Autosync.** Off by default. When enabled, the owning process pulls and pushes through the same verified sync engine. It halts, without retrying or resolving anything, on conflicts, signature/recipient/replay/unreadable-record errors or diverged history; only network failures, and a failed local commit for up to three rounds in a row, are retried. Files that an earlier round wrote but did not commit are committed before the next fetch only if they are ciphertext or this device's own manifest and heartbeat, and the checkout passes manifest verification; other changes are never committed or discarded. Sync health in the unauthenticated `/status` route is limited to state, timestamps and flags; error text and peer labels require the session token.

**Linux.** Linux builds are source-built previews with less runtime coverage than macOS. Electron does not report screen-lock events on Linux, so only Lock, sleep, idle timeout and closing the window lock the desktop. An unlocked login keyring hands the remembered password to any process in your session that asks the Secret Service for it. Where the kernel restricts unprivileged user namespaces and `chrome-sandbox` has not been made setuid root, the installed launcher runs Chromium with `--no-sandbox`; the renderer keeps context isolation and its IPC checks but loses the OS-level sandbox. The optional systemd user unit keeps the headless backend available after the desktop closes, with the same remembered-password limits.

**Metadata.** Names, usernames, emails, URLs, notes, expiry dates, and project counts are visible through metadata scopes and may enter agent conversations. Do not place credentials in metadata. The private-permission local audit log contains names, actions, actors, and times, not secret values; it is plaintext and is not tamper-evident. Encrypted history retains previous values for up to 2,000 changes. Deletion is not secure erasure of backups/history.

**Sync is a separate encryption boundary.** Local `sync-age.key` and `sync-signing.key` files are stored with mode 0600, not encrypted with the vault passphrase. Someone who steals the age key and sync repository can decrypt synced records. Vault password rotation does not rotate these keys or protect old Git history. Every trusted peer is a full participant with all synced records, not a per-project collaborator. Signed manifests expose counts, opaque identifiers, hashes, labels and timing; low-entropy content can be susceptible to guessing via content fingerprints. Use a private repository. First contact needs independent identity verification; rollback detection depends on retained local state and is not a transparency log.

**Availability and durability.** Remote failures, local disk loss, interrupted writes and concurrent edits may prevent progress. Atomic writes and stale-writer checks reduce accidental overwrites but do not replace tested backups. Password rotation across multiple backup files is not transactional; verify its per-file results and retain both passwords until complete. No recovery service exists. A pull that changes the vault first copies `vault.enc` to `backups/`; the newest 20 of those copies, and any from the last 30 days, are kept and older ones are deleted, so keep your own backups for anything older.

**History.** To support Revert, the encrypted vault's history keeps each change's old and new values, including secret values. It is capped at 2,000 entries or 1 MB, whichever is reached first, by dropping the oldest. A copy of the vault or a backup includes that history.

## Format v4 (Rust core)

`crates/vaultos-core` implements the next vault format. The headless Rust programs (`vaultosd`, `vaultos`, `vaultos-agent`, `vaultos-mcp`) use it; the desktop app does not yet, and everything above describes format v3 and the Node programs. See [the architecture notes](docs/ARCHITECTURE.md#rust-core-format-v4) for the key hierarchy.

- **Unlocking.** Argon2id (256 MiB, 3 passes, 4 lanes; about 0.9 s on an Apple M2) derives a key from the master password, and HKDF-SHA256 turns it into the Account Unlock Key. The parameters are read before anything is authenticated, so a file asking for less than 19 MiB and 2 passes, or for more than 1 GiB, 16 passes, 16 lanes or four times the default's memory × passes (a few seconds), is refused before Argon2id runs. The Account Unlock Key unwraps a random Vault Key, so changing the password re-wraps one key and re-encrypts nothing else.
- **Secret Key.** Optional, chosen per vault: 128 random bits shown as `VK1-` and 30 Crockford base32 characters with a 20-bit checksum. With one, the Account Unlock Key needs both the password and the Secret Key, so a stolen vault file cannot be guessed at from the password alone. The file stores only a 32-bit fingerprint, to say which key is missing. Losing both the Secret Key and every unlocked device loses the vault; there is no recovery service.
- **Encryption.** The Vault Key wraps one key per project. Item metadata and item secrets are sealed separately with XChaCha20-Poly1305 and a random 192-bit nonce; the associated data names the purpose and the vault, project and item ids, so a box copied to another place in the file does not open. Listing and searching decrypt only metadata.
- **Integrity.** The whole file carries an HMAC-SHA256 under a key derived from the Vault Key. Removing, reordering or rolling back any part, or adding unknown fields anywhere (sealed boxes included), fails the unlock. This does not detect replacement of the whole file with an older complete copy (for example, a restored backup).
- **Audit chain.** `audit-v4.log` lines are Ed25519-signed and each names the hash of the line before it. The signing seed is sealed under the Vault Key and its public key is in the file, and every save records the newest entry in the vault, so editing, reordering or cutting the log short is detected. Entries written after the last save can be lost unnoticed. Anyone who can unlock the vault can sign new entries; the chain shows tampering by someone without the password, not by its owner. Appends, resets and set-asides take one lock (`.audit-v4.log.flock`) and appends follow the last entry on disk, so two processes writing to one vault keep a single chain. A log that fails verification at unlock is checked again, under that lock, before the next save or audit entry. If it is sound by then it simply continues; if another process reset it after this one unlocked, that new chain is followed; otherwise it is moved aside (`audit-v4.set-aside-*.log`) and a new chain starts with a signed `audit_log_reset` entry naming the problem, which that save anchors. A save never records "no head" over a damaged log. Entries hold names, actions and actors, never values. An entry is written before the change it records is saved, so a failed save can leave an entry for a change that did not happen, never a change without one. A new agent or approver token is written to its file only after the vault saves it.
- **Memory.** The Vault Key and keys derived from it are held in locked memory where the OS allows (`mlock`), are zeroed when dropped and are never printed by `Debug`. The sync identity (age key and signing seed) is zeroed when dropped and never printed, but is held in ordinary memory for as long as the vault is unlocked, so the OS can swap it to disk. Passwords, Secret Keys, sealed-secret plaintext, revealed values and decrypted records are zeroed when dropped; delegating, adopting and approving change metadata without opening the secret. A value being edited, restored by Undo or carried through an upgrade also passes through JSON values (history payloads) that are not zeroed. `hardening::harden_process`, for the programs that will use the core, turns off core dumps, makes the process undumpable on Linux (no same-user `ptrace` or `/proc/<pid>/mem`) and, in release builds on macOS, refuses debugger attachment. Software running as your account, root or a compromised OS still reads an unlocked vault.
- **Upgrading.** Nothing upgrades automatically. `upgrade::upgrade` runs only when the owner asks: it copies `vault.enc` to `backups/vault-v3-<time>-<hash>.enc` and flushes it to disk, writes the new chain's first audit entry, decodes the new file again with the password and compares it with the original (history must match exactly, less only the oldest entries the 1 MB cap would drop), and replaces the vault last, only if it did not change meanwhile. An error therefore leaves the v3 vault in place, except one saying the change was saved but not confirmed on disk: then v4 is in place (the same holds for every save, which keeps its new state and any new password or Secret Key in that case). `audit.log` is left as it is, with the v3 backup. The backup is readable by the earlier app with the earlier password. A v4 vault cannot be opened by the JavaScript app, and devices syncing one vault must use the same format.

### The Rust daemon

- **Transport.** `vaultosd` serves HTTP/1.1 on a Unix socket, `vaultosd.sock` in the private data directory, or, when that path is too long, in `$XDG_RUNTIME_DIR/vaultos` or `vaultos-UID` under the temporary folder, which must be a real directory owned by you with no group or other access. It refuses connecting processes of another user (checked with the peer's credentials) and requests with browser headers. Every route except `/status` needs the random session token in `daemon.json` (mode 0600); agent routes also need an enrolled agent token. Clients accept only a `daemon.json` that names this data directory's socket or its private fallback. Agent permissions are enforced in `vaultosd`, as in `api.js`; the MCP bridge and `vaultos-agent` hold no vault state.
- **Owner controls.** The session token authorizes `/unlock`, `/lock`, `/shutdown` and `POST /sync`. Requests carrying an agent token are refused on these routes, so an agent cannot sync, lock or stop the daemon through its own grants. The session token is readable by software running as your account; these are local-account controls, not agent permissions.
- **Starting.** `vaultosd` starts locked, and nothing starts it for an agent. There is no remembered password or Keychain unlock for the Rust tools yet; a human runs `vaultos unlock`, which sends the password over the socket. `--idle-lock-minutes` locks it after that long without a request; it does not observe screen lock or sleep. Its log, `vaultosd.log`, holds operational messages, not values.
- **Status.** `/status` without the session token reports only whether the daemon runs, is locked, its version and format, and public sync health (`enabled`, `state`, `halted`, `lastSyncAt`, `peerStalled`). Sync errors and peer labels need the session token.

### Sync format 2

- **Keys.** Each device's age X25519 identity and Ed25519 signing seed are sealed inside the encrypted vault (`sync_keys`), with the trust pins. Stealing the data directory and the sync repository without the password (and Secret Key, if set) does not decrypt synced records. Password rotation re-wraps the vault key but does not change these keys or protect old Git history.
- **Repository contents.** Records and tombstones are age files encrypted to every recipient in `recipients.txt`, under names that are the SHA-256 of their record ids. Every recipient must be a device this one trusts, or encryption is refused. Manifests are Ed25519-signed lists of ciphertext digests with a counter per device. Each file entry names the push (device and counter) that wrote that ciphertext, and each manifest records the newest push of every other device it had accepted. They carry no plaintext hash or content fingerprint, so the repository does not enable guessing low-entropy values. They still expose record counts, device labels and ids, timing and ciphertext sizes. Signatures are domain-separated from each other and from the audit chain.
- **Verification.** A pull or push refuses unsigned or modified ciphertext, unknown files in sync's folders, untrusted or changed device keys, a manifest whose counter went backwards, and a committed `.gitignore`, `.gitattributes` or `.gitmodules` anywhere in the checkout. A file is accepted only if a manifest signs it and no manifest that had seen the push which wrote it lists it differently or not at all, so an older ciphertext put back from history is refused even when a stale manifest still signs it. A manifest that names a push newer than that device's manifest in the checkout, or a device whose manifest is missing, is refused as a rollback. A push refuses to commit when Git would store other bytes than sync wrote (a filter or line-ending rule in `.git/info/attributes`, say), and refuses to push over a rebase that brought in a Git control file. A missing file is refused while any manifest still lists it as current, even if a tombstone of the same name exists.
- **Rollback limits.** The local index (`sync-index.json`) is keyed and authenticated with keys derived from this device's signing key: it holds no plain record hashes, and a modified one stops sync. It also remembers the newest manifest seen from each device. Without it, a device can be shown a complete, consistent older state of the repository that no other manifest contradicts; the manifests' seen counters catch a rollback only when another device had already seen the newer push. `vaultos backup` copies the index with the vault, so a restored device keeps that memory. This is not a transparency log.
- **Merging.** A deletion yields only to a later edit (the record's `updatedAt`), on either device, not to a later push of the same record, so a device that missed the deletion and re-encrypts the record cannot bring it back, and an edit made after the deletion is kept everywhere.
- **Trust.** First contact needs out-of-band comparison of identity fingerprints. Every trusted device is a full participant with all synced records. There is no revocation yet: removing a device or rotating keys means a new sync repository and new enrolments.
- **Autosync.** Off by default and enabled only by the human (`vaultos sync auto on`). It retries only network failures, a busy vault and, up to three times, a failed commit; anything else halts it with an audit entry (`sync_halted`) until a human acts. It never accepts conflicts. A pull that changes the vault first backs up `vault.enc` and applies all changes in one save. Git's error text is logged and audited with any user name, password or query string in a remote URL masked. Stopping `vaultosd` waits for a round in progress (each Git command has its own time limit) before it locks the vault and releases it.

## Assurance

This is an unsigned, unnotarized preview, not an independently audited password manager. Automated tests cover encryption failures, stale writes and reloads, ownership/scopes, HTTP authentication, owner-only sync requests, service ownership handover, unsafe export paths and shell values, sync tampering/replay/conflicts, autosync halting, Touch ID confirmation gating (with a simulated sensor), and the desktop lock flow. Tests and dependency advisories cannot establish that all vulnerabilities are absent. See release notes for exact validation and outstanding platform coverage.

The implementation follows the [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security). Contributions that weaken these boundaries require explicit design discussion and regression coverage.
