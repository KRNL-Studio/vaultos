# Architecture

VaultOS is a Rust workspace. Every program uses `crates/vaultos-core` and vault format v4.

```text
Human → window / Quick Access (renderer/, system web view)
            │ two Tauri commands, checked per window and page
            ▼
        VaultOS (vaultos-desktop) ─┐            ┌─▶ vault.enc (v4), audit-v4.log
                                   │ owns,      │
Human → vaultos (CLI) ─────────────┤ one at a   ├─▶ vaultos-core
                                   │ time       │
        VaultOS --service ─────────┤            └─▶ vaultos-sync ─▶ age + signed Git sync
        vaultosd ──────────────────┘
            ▲  HTTP over a Unix socket (daemon.json token, same-user peers only)
            │
Coding client → vaultos-mcp      Shell agent → vaultos-agent      Browser extension → vaultos-browser
```

| Crate | Role |
| --- | --- |
| `vaultos-core` | Format v4, the store, the audit chain, the v3 upgrade, file safety, process hardening. `sites.rs` matches pages to saved logins by registrable domain (the vendored Public Suffix List), `store/browser.rs` keeps browser pairings and finds, fills and saves logins, and `native_host.rs` registers the browser helper |
| `vaultos-daemon` (`vaultosd`) | The owner's server. `server.rs` serves HTTP/1.1 (hyper, tokio) on `vaultosd.sock`, accepts only peers with this user's id, and requires the session token from `daemon.json` on every route but `/status`. `api.rs` authorizes each agent request independently for scopes, project and folder grants, just-in-time grants and approvals; for `POST /run` it checks the command and reads the values, and `server.rs` then starts the command in the owner, so the agent gets only its masked output. `human.rs` serves `POST /human/values` to `vaultos read`, `render`, `run` and `scan`, confirmed per request with the password or the app's Touch ID. `access.rs` keeps just-in-time grants in memory, `ssh_agent.rs` is the opt-in SSH agent on `ssh-agent.sock`, and `browser.rs` serves the browser extension's `/browser/*` routes (pairing confirmed by the human; every other route needs the pairing key from the paired extension's origin; agent tokens refused). A guard loop restores `daemon.json`, reloads `vault.enc` when another writer replaced it and applies the idle lock. `autosync.rs` runs sync rounds, holding the store only for their local steps. `run_embedded` lets the desktop and service mode run the same server in-process |
| `vaultos-client` | Finds the owner through `daemon.json` and a trusted socket path, discovers the agent token and maps errors to exit codes. It never starts an owner. `run.rs` starts commands with masked output, and `ssh.rs` talks to an SSH agent's socket |
| `vaultos-mcp` | The stdio MCP bridge (rmcp) with the tool names and schemas in `tools.json`. It keeps no vault state; each tool call is one owner request |
| `vaultos-cli` (`vaultos`, `vaultos-agent`, `vaultos-ssh-sign`, `vaultos-browser`) | The human CLI, which opens the vault itself for admin and sync commands and talks to the owner for `start`, `unlock`, `lock`, `stop`, `status`, `sync now` and, while it runs, `read`, `render`, `run` and `scan`; the agent shell client; Git's SSH signing program; and the browser extension's native messaging host, which relays length-prefixed JSON from the browser to the owner and keeps nothing |
| `vaultos-sync` | Sync format 2: `lib.rs` encrypts, signs, verifies and merges; `git.rs` runs Git with argument arrays, disabled hooks and known paths only |
| `vaultos-desktop` (`VaultOS`) | The Tauri v2 app (below) |

## Desktop

`main.rs` builds the Tauri app; `commands.rs` holds the two commands the pages call, `vault` for the main window and `quick` for Quick Access. `from_page` accepts a call only from its own window label at its own page (`index.html` or `quick.html` on the app's origin), so Quick Access cannot reach settings, agents or sync, and every non-public call needs the human's unlock and resets the idle timer. `renderer/tauri-bridge.js` gives the pages the `window.vault` / `window.quick` objects they use, over those commands. The pages never receive a value unless the human reveals or edits it; copies go through `platform.rs`, which on macOS writes concealed, transient, current-host-only pasteboard data and clears it only if unchanged.

`app.rs` keeps the state and lock rules. Unlocking claims `owner.lock` by starting the daemon's server in-process (`run_embedded`), so enrolled agents are served while the window is unlocked; the window's own calls reach the store through the server's handle, never the socket. Every lock bumps a generation, so an unlock still waiting (for its turn, for Touch ID, for another process to hand over the vault) cannot finish after a later Lock. A full Lock stops the server, clears the window, Quick Access and the clipboard, and, for Lock and the hard lock policy's screen lock, sleep and idle, writes the `locked` block and removes the remembered password. Closing the window locks without the block. A soft lock only locks the window. Human-only actions pass `gate`, which requires a recent Touch ID or master-password confirmation when `touchId.humanActions` is on.

`ui.rs` owns the windows, the menu bar item, the application menu, the Quick Access shortcut, notifications and the watch loop (every 2 seconds: idle, screen lock, a gap in its own clock after sleep, and a server that stopped underneath). `platform.rs` adds the macOS will-sleep and session-resign observers, Touch ID through LocalAuthentication, `enclave.rs` the Touch ID unlock's password copy sealed to a Secure Enclave key, and logind's `LockedHint` on Linux. `keyring.rs` stores the remembered password and the Secret Key in the macOS Keychain (Security framework) or the Secret Service (`secret-tool`), in the preview's namespace, with no plaintext fallback. `prefs.rs` validates the plaintext `desktop-prefs.json`, `login.rs` writes the opt-in LaunchAgent or XDG autostart entry, `search.rs` ranks metadata without values, `export.rs` writes the encrypted PDF export, `items.rs` handles the Trash, generator, one-time code, attachment, version, Watchtower, breach-check and import calls (with `renderer/items.js` on the page side), and `settings.rs` validates the vault's encrypted settings.

`service.rs` is `VaultOS --service`: the same program without Tauri, for the LaunchAgent or systemd unit. It waits while another process holds `owner.lock` or the `locked` block exists, reads the remembered password in a blocking task, runs the embedded server and unlocks it, and returns to waiting when the window asks it to stop (standing back 10 seconds so the window can claim the vault) or when the vault locks underneath it. Conditions a restart cannot fix exit 0.

## Browser extension

`extension/` is a Manifest V3 extension with no build step. `background.js`, the service worker, is the only part that talks to VaultOS: through `chrome.runtime.sendNativeMessage` (or a port while a pairing waits for the human) to `vaultos-browser`, which the browser starts with the extension's origin. It keeps the pairing key in the extension's IndexedDB, takes each page's address from the message sender, and accepts the popup's operations only from the popup and page operations only from content scripts. `content.js` runs in every frame of HTTPS and localhost pages: it shows the fill button and menu in a closed shadow root, types the chosen login with input events, and reports submitted logins for the save offer, which the worker keeps in session storage. `shared.js` holds its DOM-free helpers. The extension's ID is fixed by the public key in `manifest.json`, which the helper's manifest names as its only allowed origin. `safari/` holds the Safari app extension: `SafariWebExtensionHandler.swift` receives the extension's native messages and runs the bundled `vaultos-browser` with Safari's fixed origin, under the sandbox in `extension.entitlements`; `scripts/package-mac.mjs` builds it with `swiftc` into `Contents/PlugIns/VaultOS Safari.appex`, with the extension and a Safari manifest in its resources. In Safari `content.js` shows no in-page controls, since it cannot check they are uncovered.

## Vault format v4

```text
master password ─Argon2id─┐
Secret Key (optional) ────┴─HKDF─▶ Account Unlock Key ─unwraps─▶ Vault Key
                                                                  ├─▶ per-project keys ─▶ item metadata, item secrets
                                                                  ├─▶ vault metadata, history, audit signing seed
                                                                  └─HKDF─▶ file MAC key
```

`format.rs` defines the file and key derivation; every box is XChaCha20-Poly1305 with associated data naming its purpose and the vault, project and item ids, so a box moved elsewhere in the file fails to open. `store.rs` holds projects, items, ownership, delegation, injection approval, history with Undo, tombstones and settings. While unlocked it holds decrypted metadata, and item secrets stay sealed until `reveal`. Each change is applied to a copy of the state and kept only once the file is saved; saving takes `write.lock`, refuses a file that changed since it was read (device, inode, size, modification and change times, or the contents where the file system keeps whole-second times), and replaces the file atomically, flushing the file and its directory. Lock files are pid files that VaultOS 0.2 also understood, and Rust processes also hold a `flock` on a companion file (`.write.lock.flock`, `.owner.lock.flock`), which the kernel releases when a process dies, so two of them can never both take over a stale pid file. A stale pid file is taken over by renaming it aside and deleting it only if it still names the dead process; a lock created in the meantime is put back with a hard link, which never replaces a file (if that fails, it is left beside the lock as `*.stale-*` and the claim fails). Delegating, adopting and approving change item metadata only (history action `update_meta`), without opening the sealed secret. `store/items.rs` adds the Trash, attachments, per-item versions, Watchtower, one-time codes and imports on top of it: items carry a type, tags, a favorite and archived flag, a Trash date and custom fields, all left out of a record when empty so earlier records keep their hashes, and secret custom fields travel inside the sealed secret. Attachments are separate sealed files under `attachments/`, named in the item's metadata. `refs.rs` parses `vault://` references and fills templates, `mask.rs` masks values in a program's output streams, `leak.rs` builds and scans the keyed-hash leak index, and `ssh.rs` reads and writes OpenSSH Ed25519 keys and speaks the agent protocol and SSHSIG; `store/run.rs`, `store/leak.rs` and `store/ssh.rs` give them values from the store. `totp.rs` computes RFC 6238 codes, `generator.rs` makes passwords, passphrases and PINs and estimates strength, and `import.rs` turns 1Password, Bitwarden and CSV exports into items without touching the vault. `audit.rs` writes the signed, hash-chained `audit-v4.log`. `upgrade.rs` is the explicit v3-to-v4 upgrade, and `v3.rs` reads format v3 only for it; `tests/fixtures/v3-vault.json` is a vault written by VaultOS 0.2 with synthetic values, which the upgrade tests read. `canon.rs` keeps 0.2's record hash (`tests/fixtures/record-hash.txt`).

Sync format 2 keeps the device's age and Ed25519 keys in `VaultMeta.sync_keys`, inside the encrypted vault, and its trust pins beside them. The local index is keyed and authenticated with keys derived from the signing key, so it holds no plain record hashes. `Store::apply_sync` writes every change of one pull in a single save. See [the sync guide](SYNC.md).

See [SECURITY.md](../SECURITY.md) for trust boundaries and limitations. Tests cover persistence and the upgrade (`vaultos-core`), socket authorization and the agent API (`vaultos-daemon`), the MCP transport (`vaultos-mcp`), the CLIs, encrypted sync, and the desktop flow and service mode (`npm run test:desktop`), rather than trying to establish security through UI tests alone. `fuzz/` holds the fuzz targets (its own workspace, built against the main lockfile by `scripts/fuzz.sh`), and `tests/vectors.rs` in `vaultos-core` the format's known-answer vectors, described in [docs/audit/CRYPTO.md](audit/CRYPTO.md).
